# atomize schema —— 原子化的真源

PM 2026-08-22 定的三条,这份 schema 就是它们的落地:

- 原子化的真源是**数据表**,不是文件
- **非内容层不进题库**;题库只要内容层
- **入题库不归原子化技能** —— 那是一次转化,归题库线的导入功能

落法:与题库**同一个 Postgres 实例、独立 schema**。平台已是「一引擎多 schema」,
运维成本≈0,边界仍硬:题库的迁移碰不到这里的表,反之亦然。

## 十一张表

| | |
|---|---|
| `sources` | 源文件。`file_sha256` 唯一——哈希才是「同一份源」的判据,文件名不是 |
| `blocks` | **物理块**,`(source_id, locator)` 唯一。「每个字符都有归属」的底座 |
| `spans` | **字符区间 → 归属**。判准是字符级不是段级 |
| `units` | **内容模块**(树)。`kind` 外键到 `unit_kinds` |
| `blanks` | **填空的空**(QTI: `textEntryInteraction`) |
| `figures` | 图。横跨两层,故单独一张 |
| `media` | 图的哈希与指针;二进制落对象存储 |
| `layout_facts` | **非内容层**,逐属性 `(source_id, locator, layer, run_index, key) → value` |
| `unit_kinds` | 模块类型词表(**数据,不是 CHECK**) |
| `templates` | **模板表(判据真源)**。题库的 `carve_templates` 是它的投影 |
| `runs` | 每次原子化的台账 + 门结果 |

## 四条判据由数据库自己守(不靠代码记得)

```
spans   EXCLUDE 同块内区间不得重叠   一个字符只能有一个归属,重叠等于没归属
figures scale_to_body_font NOT NULL  只记绝对尺寸,图片大小必然漂移
units   kind → unit_kinds 外键        未登记的类型插不进去(含把「知识点」当模块)
spans   CHECK char_end > char_start   空区间不是归属
```

★ 第三条顺带守住了 PM 那句「标题不是知识点」:`知识点` 不在 `unit_kinds` 里,插不进去。
原子化只记结构——这道题落在哪个标题下、标题原文是什么;它是不是知识点、叫什么名字,**是后面的事**。

## 借了 QTI 3.0 的两条

[QTI 3.0](https://www.imsglobal.org/spec/qti/v3p0/oview)(1EdTech)是评测内容交换的国际标准,
我们的模块几乎与它一一对应,`unit_kinds.qti_equivalent` 逐条记着。其中两条直接改了做法:

1. **`units.max_choices`** —— 单选/多选**声明出来**,不靠数答案里的字母。
   2026-08-21 实测:21 道被判多选的题里 13 道是「（1）C；（2）3.7 m/s」这样数出来的,
   而全语料里真正标注多选的只有 8 处。**数出来的判据会骗人,声明的不会。**
2. **`blanks`** 对应 `textEntryInteraction` —— 「填空的空」在标准里本来就有名字,不用自己造。

## 验

```bash
PGHOST=127.0.0.1 PGPORT=25432 PGUSER=czclass ./check_schema.sh
```

建临时库 → 跑 `001_init.sql` → 逐条**先验红**(插一条它该拒的)→ 再验绿 → 删库。

★ 为什么必须真跑:首版 SQL 读起来没问题,一跑就炸 ——
`spans` 的 `EXCLUDE` 要在 GiST 索引里对 `bigint` 做等值比较,而 `bigint` 默认没有 gist 操作符类,
得先 `CREATE EXTENSION btree_gist`。**读代码看不出来,只能让数据库说话。**

## 首次落库实测(2026-08-22,物理教师版)

链先重跑了一遍(外置树删后从 `~/Downloads` 的源重建):**原子化 13 步全 ok,
`GATE_RECONSTRUCTIBLE: pass`,20 档,`losses: {}` 零损失**;
`atoms.normalised.json` / `layout.json` / `structure.json` 与被删的原件**字节数逐一相同**——
「可再生」这个判断有了实证。

`persist_atomize.py` 首次落库:

| | |
|---|---|
| blocks | 5,351 |
| layout_facts | 54,585(rPr 33,074 · pPr 21,351 · sectPr 160) |
| units | 2,396 |
| spans | 1,028 |
| figures | 203(相对比例 2.81–19.50 倍正文字号,均值 8.97) |

### 四个缺口的修复(2026-08-22 同日)

| | 修前 | 修后 |
|---|---|---|
| 图能算出相对比例 | 88 / 1047 | **1045 / 1047** |
| 图写进库 | 203 | **876** |
| 字符归属 | 10.38% | **96.0%** |
| spans | 1,028 | **6,041** |

怎么修的:

- **VML 的尺寸写在 style 的 CSS 串里**(`height:26.75pt;width:18.95pt`),不在 `<wp:extent>` 标签里。
  此前只把 style 原样记下没解析 —— 342 张 VML 图因此一张都算不出比例。**记了 style 不等于记了尺寸。**
  认不出单位的(4 处)不猜,留给普查报出来。
- **正文字号要沿样式继承链解**(直接 rPr > 段落样式含 basedOn 链 > docDefaults)。
  实测 820 个带图的块里**只有 42 个有直接 rPr 字号,778 个来自样式** —— 旧代码对 95% 的情况是瞎的。
  解析放在非内容层(`capture_layout`),不放在持久化步骤:那是非内容层该记的事实,两处各解一遍必然漂。
- **选项标签归给它后面的选项。** 引擎的 `range` 指选项正文不含标签,标签也是字符,也得有归属。
- **没有任何原子认领的块**(档标题、栏目横幅、知识点标题、横幅下的引导正文)建成 `heading`/`prose` 单元。
  「不属于任何一道题」不等于「不用记」——编制成册要排它们。

### 表格:两层都没进去过

`w:tbl` 此前只记了表级属性(`tblPr` / `gridCol` / `tcPr`),**单元格里的段落一条都没记** ——
里面的 `pPr`/`rPr`/图形没有,字也就无从归属。**「记了这张表」不等于「记了表里的东西」。**

补上单元格遍历(约定 `body/tbl[n]/tr[r]/tc[c]/p[i]`,**非内容层与归属遍历共用同一套**——
两层各写一套键必然全对不上,这条踩过一次)之后:

| | 补前 | 补后 |
|---|---|---|
| 非内容层条目 | 5,351 | **6,382**(表内段落 1,031) |
| 非内容层事实 | 54,585 | **60,706** |
| 源里的图 | 1,047 | **1,074**(表格里还藏着 27 张) |
| 字符归属 | 96.0% | **99.13%** |
| spans | 6,041 | **6,897** |
| figures 入库 | 876 | **903** |

表内段落归给**拥有那张表**的原子(原子认领的是整块 `body/tbl[n]`),651 条;
不属于任何原子的结构块(档标题/栏目横幅/知识点标题)建成 `heading`/`prose`,470 条。

### 再往下收(同日)

| | | |
|---|---|---|
| figures 入库 | 903 → **1046**(源里 1074) | 未认领单元改到 figures **之前**建,图才有主人可挂;纯图片段(段内无字但有图)也建 `figure` 单元 —— **「这一段没有字」不等于「这一段没有内容」** |
| 字符归属 | 99.13% → **99.19%** | 整块归属改用**源**里那块的真实长度(引擎记的 text 是规整过的,比源短,块尾会剩一截永远盖不到) |

★ 中途归属率算出 **100.87%** —— 比 100% 还高。查下去是 44 个 `body/tbl[n]` **容器块**
自身无文本却挂了 3,426 字符的 span:表格的字被数了两遍(容器一遍、单元格段落一遍)。
**容器不是文字载体。** 现在 `add_span` 对源里没有文本的块直接拒绝并计数,不静默。

同时把源文本存进 `blocks.text` —— 此前存的是空串,于是**没有任何东西能验 span 是否越界**。
存了才验得了。

### ★ 仍然缺的

- **1,657 个字符无归属**(203,678 里,99.19%)。
- **26 张图所属的块没有归属到任何原子**(1074 张里)。
- 2 张 VML 图的 style 里尺寸没有单位,不猜。

★ 中途差点自己骗自己:把分母从「整份源」换成「我数得着的那些块」,归属率立刻从 96% 涨到 99.11%。
**那不是归属做多了,是分母做小了。** 把分母做小是最容易骗过自己的量法错——数字变好看,缺口原封不动。

### ★ 落库逼出来的四件事(都不是「差不多了」)

**① 引擎的原子 id 是内容哈希,不唯一。** 796 条里 5 个 id 各撞 2 次——同一讲里逐字相同的
讲解条目(如「1. 质量的单位」同时在 `body/p[16]` 与 `body/p[65]`)。内容相同是事实,
但它们是两个不同的**出现**。主键改取 `(source, document, locator)`(实测唯一),
内容哈希留在 `meta.contentHash`。

**② 字符归属只有 10.38%**(169,012 字符里 17,538)。这一版只落了选项的区间——
引擎已经给了 `range`;题干/小问/答案解析尚未逐字符定位。
**低就是低。** 段落级曾报 100%,那是把差距盖住了。

**③ 选项标签没有归属。** 引擎的 `range` 指「选项正文」,不含「A．」「B．」。
要做到每个字符都有归属,标签得单独归给选项。

**④ 962 张图里 722 张算不出相对比例:**

```
342  VML 图形     非内容层根本没捕获它的尺寸(只记了 kind=vml)——「逐字捕获」的真缺口
617  缺正文字号   字号来自样式继承链,现实现只看直接 rPr,没沿样式解析
 88  可算
```

★ 这两条是 `scale_to_body_font NOT NULL` 逼出来的。若那一列可空,722 张会静静地写进去、
带着 null 的比例,**没有人会知道**。判据写进 schema 的价值就在这里。

另:29 个选项的 `range` 是零宽——那是**图片选项**(内容是图不是字),不是缺陷,
故不造假区间填补,图的归属走 `figures`。
